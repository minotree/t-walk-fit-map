# 사진 응답 시간 측정

2026-10-21. 사용자 요청으로 로컬 PC의 Node 24 fetch에서 운영 공개 API와 공개 지점 사진 5개·연결된 도감 사진 5개를 측정했다. 데이터·파일·버킷은 수정하지 않았다. 서명 URL 발급은 60초 유효기간으로 수행했고 키·객체 경로·토큰은 출력하지 않았다.

## 사진 다운로드 결과

용량은 실제 받은 바이트를 KiB로 반올림했다. 첫 요청은 이 측정 프로세스의 첫 다운로드이며 CDN 최초 요청을 뜻하지 않는다. 반복은 동일 URL을 즉시 다시 GET한 결과다. Node는 브라우저의 디스크 이미지 캐시를 사용하지 않는다.

반올림 때문에 헤더·본문 합과 총 시간이 1ms 정도 다를 수 있다. 헤더까지 시간은 DNS·연결·TLS·네트워크·CDN/서버 대기를 포함하며 DB나 서버 처리 시간만을 의미하지 않는다. 비교 사진의 내용·크기·캐시 상태가 달라 포맷 변경만으로 같은 비율의 개선을 보장하지 않는다.

## API 결과와 해석

- 공개 지점 목록 첫 조회 854ms.
- 대표 사진 RPC 첫 조회는 지점 순서대로 494/162/482/167/177ms, 반복 조회는 185/163/452/159/170ms.
- 서명 발급은 184/204/198/171/173ms.
- 설치 기구 조회는 476/437/462/178/460ms. 이 측정에서는 구간 분리를 위해 순차 호출했으며 앱의 병렬 처리 전체 시간을 재현하지 않는다.
- PNG 3개는 본문 전송만 609~692ms로 용량 경량화 대상이다. WebP도 MISS에서 헤더 대기가 520~550ms 있으므로 용량만의 문제가 아니다.
- 같은 서명 URL의 반복 요청에서 CDN HIT와 짧은 응답을 확인했지만, 이는 앱 재진입 속도나 브라우저 디스크 캐시 성능을 직접 측정한 결과가 아니다.
- 기구 사진은 이번 요청부터 CDN HIT였다. 토스에서의 기구 상세 DB 조회·이미지 디코딩·화면 반영·실제 모바일 네트워크는 미측정이므로 기구 지연 원인을 확정하지 않는다.

## 다음 개선 대상

1. 관리자 사진 저장 경로에서 PNG가 생기는 지점을 확인하고 사용자 표시용 WebP/축소본을 새 경로에 생성하는 방식을 검토한다. 대상은 우선 큰 PNG 3개이며 사진 가독성과 실제 용량을 비교한다. 관리자·조사 프로젝트는 읽기 전용 범위이므로 이번에 수정하지 않았다.
2. 원격 파일 교체는 새 파일 업로드→DB 경로 변경→참조 확인 후 이전 미사용 파일 삭제 순서와 별도 승인 범위를 따른다. 기존 원본을 덮어쓰거나 일괄 삭제하지 않는다.
3. 토스 실제 기기에서 화면 진입→상세 API 완료→사진 요청 시작→다운로드 완료→표시까지 측정해 기구 사진의 지연 구간을 확인한다. 사진 로딩 표시만으로 속도 개선을 판단하지 않는다.

앞선 요청 병렬화·서명 URL 재사용 변경에 대해 사용자는 체감 속도가 비슷하다고 보고했다. 이번 결과는 해당 피드백 후의 진단이며 새 최적화의 기기 검증 완료를 뜻하지 않는다.
